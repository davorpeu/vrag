# W6 report: repo activity ("what was done recently, in which files")

## 1. What I did and decided
A separate feature next to the document versions. It reads a repo's commit history, indexes it in its own ES index,
and answers "what was done recently / in which files" for a time window.

- **Reading git** (`src/vrag/activity.py`): `git log --numstat --no-merges --no-renames` gives, per commit, sha, date,
  author, message (subject + first 300 chars of the body) and files with +/- lines. Merges are skipped (their files
  show in the merged commits). Renames are not followed, so numstat paths stay plain. A commit keeps at most 500 files
  (`files_total` has the real number).
- **Clone choice**: `git clone --no-checkout --no-tags --shallow-since=<window start - 7 days>` into
  `data/repos/_activity/<owner>__<name>` (already gitignored; separate from `data/repos`, so `ensure_clone` and the
  document flow are untouched; `remote.py` is only used through `parse_link`/`GITHUB`). Why: only the window is
  needed, and with a shallow clone all blobs are local, so numstat is one fast local call. A blobless clone would
  fetch blobs one by one. No checkout = no working tree. After clone/fetch, `fetch --deepen=1` gives the oldest
  window commit a real parent, so its numstat is a real diff, not "whole tree added" (tested). Live sizes: fastapi
  19 MB, ollama 33 MB.
- **Index** (`ACTIVITY_INDEX`, default `vrag-activity`, read with `os.getenv` in `activity.py`): one doc per commit
  (`_id = <repo>:<sha>`, embedding of message + up to 40 file paths) and one `repo:<key>` doc (url, loaded-since,
  synced_at, commit count). Idempotent by sha: known shas are not embedded again. The loaded-since date never
  shrinks on a shorter later sync.
- **Window** (`parse_window`, plain code): last/past N days|weeks|months|years, "last week", yesterday, today,
  this week/month/year, since/in/during/from <month> [day] [year], ISO dates, "last N commits". "recently" and no
  period = 14 days. API/CLI can override with `days` / `last_n`. If the period starts before the loaded history, the
  answer carries a note.
- **Answer**: window commits come from ES. If the question names a topic (words left after removing time words,
  filler and the repo name), the 25 commits most related (kNN, filtered to the window) are used and a note says so.
  Files and directories are counted in code (a commit counts once per directory, dirs = first 2 path levels).
  The LLM only gets short sha | date | author | first line of message (max 100, a spread sample if more; no file names)
  and returns summary + themes with cited short shas. In code: shas not in the given commits are dropped, a theme with
  no real sha is dropped, at most 5 shas per theme, sha lists the model writes inside prose are stripped, and a
  summary saying "no changes were made" above a list of changes is replaced by a plain line. "Most changed files"
  is appended by code. Model down = the data plus commit messages, with a note. Citations link to GitHub
  (`/commit/<sha>`) when the repo is on GitHub.
- **Schema**: `ActivityAnswer` (Pydantic): answer, window, topic, commits_in_window, commits_used, authors, files
  (top 30, with total), directories, commits (up to 60, with urls), citations, notes.
- **CLI**: `vrag activity sync --url <repo> [--days 90] [--max-commits 500]`, `vrag activity ask --url <repo|name>
  "question" [--days N] [--last-n N]` (stdout set to `errors=replace`: commit messages hold emoji, which crashed the
  cp1252 console in the first live run).
- **API**: `POST /activity/sync` (202 job, same `_sync_lock` as `/sources/git/sync`, so 409 when anything else is
  loading), `GET /activity/jobs/{id}` (new, needed for polling), `POST /activity/ask`, `GET /activity/repos`.
- **UI**: a "Repo activity" toggle at the top of the sidebar (off = the document UI exactly as before). On: link field,
  "History to load" (30/90/180/365 days), Load with a progress bar (downloading / reading / indexing n of m), the
  loaded repos as a list, a chat. Each answer shows the text, notes, a "Files changed" table (path, commits, +, -)
  with directories, and a "Commits" list with links and a mark on the cited ones.

## 4. Unfinished, wrong, risks
- Found and fixed during the live run: (a) CLI crashed on emoji in commit messages; (b) the model put long
  duplicated sha lists in theme descriptions (now stripped, max 5 cited per theme); (c) with a topic the model said
  "No documentation changes were made" above its own themes (now replaced). Also "areas" counted as a topic word.
- Quality limits of qwen2.5:7b: theme descriptions are generic ("Commits aimed at stabilizing tests"), and some theme
  assignments are loose (a README commit under "Performance"). Titles and cited shas are right to check; the files
  table and counts are exact. A bigger model or a two-pass summary (cluster, then name) would help.
- Topic search is semantic over message + file paths only: "documentation" surfaced release-note and translation
  commits, not hand-written docs. Commits of a topic window are capped at 25.
- Squash-merge repos (fastapi, ollama) work well. Repos that rely on merge commits lose the merge commits' own
  messages (we skip them); their real commits are still read.
- Window start older than what was loaded: the answer says so; there is no automatic deepening.
- `sync` caps at 500 commits (newest first); a very busy repo with `--days 365` only gets the newest 500 and the
  stored "loaded since" date is then too early. Cap hit is not reported yet.
- Not tested live: the API server and the Streamlit page against real ES (UI is tested with a fake API).
- Only `main`/default branch is read (`--shallow-since` implies single branch).
